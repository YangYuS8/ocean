## 为什么

当前 `samples/:id` 已经是样本处理的主工作台，但样本还没有稳定的图像输入语义，YOLO 模型也没有一个清晰、克制的落点。若直接把模型做成自动结果生成器或完整图片管理系统，范围会明显超过当前 MVP。

我们需要先补齐一个更窄的闭环：每个样本先拥有一张主图，用户可以在样本工作台上手动触发一次 YOLO 检测，并获得一份仅供人工参考的自动检测建议。这样既能验证模型价值，也不会打乱现有“结果 / 异常 / 分析任务”分层。

## 变更内容

- 为 `sample` 引入单一主图语义，使样本在 MVP 阶段有且仅有一张可供自动检测使用的主图。
- 在 `samples/:id` 上增加手动触发 YOLO 检测的工作台能力，并继续由 `analysis_jobs` 承载检测过程状态。
- 新增“自动检测建议”消费层，用于展示基于当前主图生成的摘要和轻量结构化建议。
- 明确建议边界：检测结果仅供人工参考，不直接写入正式结果，不自动驱动异常或业务流转。
- 明确建议时效规则：主图一旦替换，旧建议保留历史但不再作为当前有效建议展示。

## 功能 (Capabilities)

### 新增功能
- `sample-image-suggestions`: 支持样本主图、手动 YOLO 检测和基于当前主图的自动检测建议展示。

### 修改功能
- `sample-analysis-job-lifecycle`: 扩展分析任务在样本工作台中的使用语义，使其可承载面向主图的 YOLO 检测尝试。

## 影响

- 前端：`samples/:id` 需要增加主图上传/展示、手动触发检测、建议状态与摘要展示。
- 后端：Laravel API 需要支持主图读写、YOLO 检测任务创建与建议查询，并保持 `analysis_jobs` 过程资源语义。
- Python：新增最小推理执行职责，将 YOLO 输出转换为“摘要 + 轻量结构化建议”。
- 数据：MariaDB 需要支持样本主图和建议结果关联；不要求在本次变更中展开完整多图媒体管理。
- 部署：继续复用当前 `docker compose`、Nuxt、Laravel、MariaDB、Redis、Python 结构；Redis 可继续作为异步边界，但不强制先做完整平台化治理。
