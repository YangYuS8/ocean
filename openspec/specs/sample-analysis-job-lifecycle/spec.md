# sample-analysis-job-lifecycle 规范

## 目的
定义样本级分析任务的最小生命周期与完成后续处理规则，使样本详情页中的分析过程从“仅有任务记录”推进到可追踪、可解释且可继续处理的 MVP 闭环。

## 需求
### 需求:分析任务生命周期主规范必须被项目文档回写
系统必须将分析任务生命周期主规范中的稳定语义同步到项目级文档中，确保项目说明与主规范对分析任务的状态机、重试语义和后续处理引导保持一致。

#### 场景:回写状态机和重试语义
- **当** 项目文档描述分析任务状态流转
- **那么** 系统必须反映 `queued -> running -> succeeded/failed`、`queued -> cancelled` 和“失败后重新发起为新任务记录”的当前主规范语义

#### 场景:回写成功和失败后的处理指引
- **当** 项目文档描述分析任务完成后的产品行为
- **那么** 系统必须说明成功和失败后的最小后续处理引导已经是当前 MVP 工作流的一部分

### 需求:分析任务必须支持最小生命周期推进
系统必须为样本级分析任务提供最小生命周期推进能力，以便在当前 MVP 阶段围绕单个样本形成可解释、可追踪的分析过程闭环。

#### 场景:任务进入执行中
- **当** 系统对状态为 `queued` 的分析任务执行开始动作
- **那么** 系统必须仅允许其推进到 `running`
- **那么** 系统必须记录任务开始时间

#### 场景:任务执行成功
- **当** 系统对状态为 `running` 的分析任务执行成功完成动作
- **那么** 系统必须仅允许其推进到 `succeeded`
- **那么** 系统必须记录任务完成时间
- **那么** 系统必须在可用时记录结果摘要

#### 场景:任务执行失败
- **当** 系统对状态为 `running` 的分析任务执行失败完成动作
- **那么** 系统必须仅允许其推进到 `failed`
- **那么** 系统必须记录任务完成时间
- **那么** 系统必须在可用时记录失败原因

#### 场景:任务取消
- **当** 系统对状态为 `queued` 的分析任务执行取消动作
- **那么** 系统必须仅允许其推进到 `cancelled`

### 需求:失败后的重新发起必须保留历史任务记录
系统必须将失败后的重新发起分析定义为基于原任务上下文创建新的分析任务记录，而不是复活原任务，以保留失败历史和多次尝试记录。

#### 场景:重新发起失败任务
- **当** 用户或系统对状态为 `failed` 的分析任务执行重新发起动作
- **那么** 系统必须保留原任务的 `failed` 状态和失败信息
- **那么** 系统必须创建一条新的分析任务记录
- **那么** 新任务必须复用原任务的样本上下文与任务类型
- **那么** 新任务必须以 `queued` 作为初始状态

### 需求:分析任务成功或失败后必须提供后续处理指引
系统必须在分析任务结束后向用户表达该过程的最小结论和下一步处理方向，而不能只停留在技术状态显示层面；项目级文档也必须将这一行为表达为当前稳定基线。

#### 场景:成功后的后续处理
- **当** 用户在样本详情页查看状态为 `succeeded` 的分析任务
- **那么** 系统必须展示结果摘要（若可用）
- **那么** 系统必须提示用户可继续录入样本结果、记录异常或暂不处理

#### 场景:失败后的后续处理
- **当** 用户在样本详情页查看状态为 `failed` 的分析任务
- **那么** 系统必须展示失败原因（若可用）
- **那么** 系统必须提示用户可重新发起分析或记录异常

### 需求:分析任务状态必须参与页面级工作台引导
系统必须将分析任务状态整合进样本详情页的页面级工作台引导，使用户能够在进入页面时直接理解当前是否仍有分析过程待完成、是否存在失败任务需要优先处理，而不是仅在分析任务区块内部发现这些信息。

#### 场景:存在待完成的分析任务
- **当** 当前样本存在 `queued` 或 `running` 状态的分析任务
- **那么** 系统必须在样本详情页的页面级工作台引导中提示当前仍有分析过程在进行中或待完成

#### 场景:存在失败的分析任务
- **当** 当前样本存在 `failed` 状态的分析任务
- **那么** 系统必须在样本详情页的页面级工作台引导中将其表达为需要优先关注的风险或后续处理提示之一
