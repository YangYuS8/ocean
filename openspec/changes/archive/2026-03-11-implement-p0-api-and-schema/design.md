## 上下文

当前 `frontend` 已完成 Nuxt 工作台骨架与导航结构，但 PHP 后端仍只有最小初始化入口，尚未形成可供前端消费的业务 API。与此同时，关于 P0 API 范围、MariaDB 数据表、接口字段和状态流转的设计文档已经在 `docs/` 中收敛完成，适合进入真正的后端与数据库实现阶段。

本次变更需要跨越多个领域：PHP API 路由与控制、MariaDB 建表与初始化数据、Redis 预留异步任务接入、Nuxt 前端与 `/api/` 的真实联调。由于它同时影响接口契约、核心数据模型和后续 Python 异步分析接入边界，因此需要一份明确的技术设计来约束实现方式。

当前部署模型保持不变：浏览器请求先进入 Nginx，页面流量转发到 Nuxt 3000 端口，`/api/` 由 PHP 提供，MariaDB 作为事务库，Redis 作为异步任务分发基础。移动端巡检场景在当前阶段主要通过响应式 Web 工作台承接，不引入原生 App 或离线数据库方案。

## 目标 / 非目标

**目标：**
- 在现有 PHP 后端中实现 P0 API 主域：`dashboard`、`inspection-tasks`、`samples`、`sample-results`、`exceptions`、`analysis-jobs`。
- 按已确认的 P0 数据表实现稿落地 MariaDB 表、索引、外键和角色初始化数据。
- 保持 Nuxt 4 Node/Nitro、Nginx、Docker Compose、MariaDB 和 Redis 现有运行方式不变。
- 让前端工作台具备从占位数据切换到真实接口的基础能力。
- 为后续 Python 分析任务消费 Redis 队列和扩展更完整认证体系预留清晰边界。

**非目标：**
- 不在本次变更中实现离线同步、GPS/围栏、视频流处理、复杂设备监控或外部平台集成。
- 不在本次变更中完成完整认证授权系统，只接受当前阶段显式传参的临时策略。
- 不在本次变更中实现高级报表、模型版本管理或对象存储编排。
- 不把 PHP、Python、MariaDB、Redis 的职责边界重新设计为新的部署模型。

## 决策

### 决策 1：按 P0 主域分层实现 PHP API，而不是一次性铺开完整业务后台
- 选择原因：当前前端工作台只需要最小业务闭环，P0 主域已经通过探索阶段冻结，继续扩展只会让实现范围失控。
- 方案内容：围绕 `dashboard`、`inspection-tasks`、`samples`、`sample-results`、`exceptions`、`analysis-jobs` 六个域建立路由和处理逻辑。
- 放弃方案：
  - 直接实现完整管理员后台、设备监控和高级报表：超出当前 MVP 范围。
  - 先实现通用 CRUD 框架再适配业务：会让状态流转和聚合接口表达变弱。

### 决策 2：MariaDB 作为唯一 P0 事务落库，按实现稿直接建表
- 选择原因：核心事务数据已经明确由 MariaDB 承担，P0 阶段没有引入额外专用存储的必要。
- 方案内容：按 `docs/2.5-P0-数据表实现稿.md` 和 `docs/2.8-P0-MariaDB-建表-SQL-草案.md` 落地 `users`、`roles`、`user_roles`、`inspection_tasks`、`samples`、`sample_results`、`exceptions`、`analysis_jobs`。
- 放弃方案：
  - 先用内存或文件 mock 存储：无法支撑真实联调和后续迁移。
  - 现在引入额外数据库或事件存储：超出 P0 范围且会增加运维复杂度。

### 决策 3：状态变化优先通过业务动作和服务端内聚逻辑完成
- 选择原因：P0 阶段已经冻结了状态流转，若只做任意 `PATCH status`，后续很难保证业务约束、审计和前端交互一致性。
- 方案内容：任务使用显式动作接口如 `start`、`submit`；样本状态在相关业务动作中由后端内聚推进；异常通过 `resolve` 动作推进。
- 放弃方案：
  - 允许前端任意更新状态字段：会破坏状态机边界。

### 决策 4：异步分析任务先做“记录与查询”，Redis 作为分发边界预留
- 选择原因：当前业务需要先有分析任务入口和状态查询能力，但不要求在本变更内完成复杂 Python 消费链路。
- 方案内容：`analysis_jobs` 在 MariaDB 中落库任务记录，PHP 接口负责创建与查询；Redis 保持为后续后台消费者预留的任务分发边界。
- 放弃方案：
  - 当前阶段直接实现完整 Python 任务调度闭环：范围偏大，且不是前端切换到真数据的唯一前提。
  - 把分析任务伪装成同步接口：不符合后续异步扩展方向。

### 决策 5：当前阶段保留显式传参身份字段，后续再迁移到认证态注入
- 选择原因：认证系统尚未实现，如果当前就把所有 API 依赖登录态，会阻塞数据库和业务 API 落地。
- 方案内容：接口层允许 `operator_id`、`entered_by`、`queued_by`、`reported_by`、`resolved_by` 等显式传参，同时在设计上明确它们属于临时策略。
- 放弃方案：
  - 先实现完整认证再开始业务 API：会放大当前阶段阻塞点。
  - 完全不记录操作者：会削弱后续审计和业务归属。

## 风险 / 权衡

- 显式传参身份字段不是真正安全模型 → 后续接入认证体系后统一改为服务端注入，并保留字段语义不变。
- 当前阶段未完成完整 Python 消费链路，分析任务可能只停留在记录层 → 先保证任务建模与接口稳定，为后续 Redis/Python 接入保留边界。
- `sample_results` 同时保留 `status` 和 `review_status` 存在理解成本 → 当前只以 `status` 作为主流程字段，避免前端使用双字段判定。
- `exceptions` 采用多态关联而非数据库级强外键 → 用应用层校验换取更低的结构复杂度。
- 样本状态采用后端内聚推进而非单独动作接口 → 实现时需要明确哪些业务动作触发样本状态变化，避免隐式逻辑分散。

## Migration Plan

1. 在 PHP 后端建立基础路由、响应结构和数据库访问层。
2. 按既定顺序创建 MariaDB 表与初始化角色/测试数据。
3. 先实现 P0 基础查询与创建接口，再补充状态推进动作接口。
4. 让 Nuxt 前端逐步从占位数据切换到真实 `/api/` 调用。
5. 使用 Docker Compose 环境验证 Nginx -> Nuxt / PHP -> MariaDB / Redis 的联通性。
6. 若实现过程中发现后端结构不满足后续扩展，可在不改变 API 契约的前提下调整内部组织。

回滚策略：
- 如果某次数据库变更或 API 实现不满足预期，可回退到仅保留已存在前端工作台和最小 PHP 初始化入口的状态。
- 在真正执行迁移时，应确保迁移脚本可独立回滚或可通过清理开发数据重新初始化。

## 开放问题

- PHP 后端将采用何种内部组织方式（轻量自定义路由、微型框架，或更完整的应用结构）仍需在实施时结合现有代码决定。
- `analysis_jobs` 是否在本次实现中同步推送 Redis 队列，还是先只落库记录，实施时可根据工作量再确认。
- 测试数据是否作为正式初始化脚本的一部分提交，还是仅作为开发辅助脚本提供，实施时需要再决定。
