## 上下文

当前 MVP 已经完成样本详情页内的结果录入，使主链推进到 `巡检任务 -> 样本登记 -> 实验结果录入`。但根据最初冻结的 P0/MVP 主链，结果之后还应承接“异常处理”，而现在样本详情页仍缺少围绕当前样本查看异常、记录异常和解决异常的能力，导致问题被发现后没有标准化入口进行记录和关闭。

当前现实约束包括：

- Laravel 已提供 `GET /api/exceptions`、`POST /api/exceptions`、`POST /api/exceptions/{id}/resolve`。
- P0 文档已明确异常是独立资源，但第一阶段主链只要求能记录、能查看、能解决，不要求复杂审核流。
- `exceptions.resource_type` 可以挂载到 `inspection_task`、`sample`、`sample_result`，但当前 MVP 需要收敛，避免样本详情页同时承担多层异常上下文。
- 样本详情页已成为处理中心，具备基本信息、结果列表、结果录入和关联工作流区块，是承接异常处理的最自然位置。
- 当前仍保留显式传参身份字段策略，因此 `reported_by` 与 `resolved_by` 可继续由前端显式传入。

因此，本次设计的重点是以最小页面增量把异常处理放进样本详情页，而不是建设独立异常平台。

## 目标 / 非目标

**目标：**
- 在样本详情页中新增异常区块，支持查看异常列表、记录异常和解决异常。
- 将第一版异常收敛到 `sample` 资源挂载，不引入多资源级异常入口竞争。
- 为异常录入限定少量固定 `category` 选项，并沿用现有 `severity` 枚举。
- 保持样本详情页在桌面端和移动端的阅读与操作流畅性。

**非目标：**
- 不在本次新增独立 `exceptions` 工作区或详情页。
- 不在本次开放 `inspection_task` / `sample_result` 级异常创建入口。
- 不在本次让异常自动驱动样本状态变化。
- 不在本次实现复杂异常审核、驳回、忽略或批量处理流程。

## 决策

### 决策 1：异常处理附着在样本详情页主内容区
- 选择原因：异常最自然地出现在结果录入和样本处理之后。将异常区块放在样本详情主内容区、紧跟结果区块之后，符合用户心智，也避免右侧栏承载过重的列表与表单。
- 方案内容：
  - 样本详情页结构调整为“基本信息 -> 结果 -> 异常处理 -> 关联工作流”。
  - 异常区块包含标题、说明、记录异常入口、展开表单和异常列表。
- 放弃方案：
  - 独立异常工作区：范围过大。
  - 将异常表单塞入右侧栏：空间不足，移动端体验较差。

### 决策 2：第一版异常仅挂载到 `sample`
- 选择原因：虽然数据模型允许异常挂在任务、样本和结果上，但 MVP 当前最稳定的处理中心是样本详情页。先固定 `resource_type = sample`、`resource_id = 当前样本 ID`，可以避免结果级或任务级异常上下文让页面和表单复杂化。
- 方案内容：
  - 记录异常时固定资源为当前样本。
  - 当前样本的异常列表通过 `resource_type=sample` 与 `resource_id=<sampleId>` 过滤展示。
- 放弃方案：
  - 同时支持 `sample_result` 级异常：需要先选择具体结果并重新组织页面层级。
  - 同时支持 `inspection_task` 级异常：偏离当前“样本处理链收口”的目标。

### 决策 3：异常分类使用极小固定集合
- 选择原因：MVP 不需要完整异常知识体系。比起自由文本或过细分类，少量固定 `category` 更利于表单简化、列表筛选和演示一致性。
- 方案内容：
  - 第一版 `category` 收敛为 `sample_quality`、`record_mismatch`、`handling_issue`。
  - `severity` 继续沿用 `low` / `medium` / `high` / `critical`。
- 放弃方案：
  - `category` 自由输入：会让命名快速失控。
  - 一次性建立大量细粒度分类：超出 MVP 需要。

### 决策 4：异常第一版同时支持“记录”和“解决”
- 选择原因：异常如果只能创建不能关闭，会让工作流停在半成品。现有 P0 接口已提供 `resolve`，因此第一版适合一并纳入，形成最小闭环。
- 方案内容：
  - 对 `open` 异常显示“解决异常”入口。
  - 解决动作保持轻量，只传最小必要字段并刷新列表。
- 放弃方案：
  - 只做记录不做解决：闭环感不足。

### 决策 5：异常状态只影响异常本身，不自动改样本状态
- 选择原因：异常出现不必然意味着样本整体状态跳转。若在 MVP 第一版就让异常自动改变样本状态，会过早引入复杂状态耦合和额外语义争议。
- 方案内容：
  - 异常创建后仅让异常自身进入 `open`。
  - 异常解决后仅让异常自身进入 `resolved`。
  - 样本状态保持由结果录入等已定义业务动作推进。
- 放弃方案：
  - 创建异常时自动把样本标记为特殊状态：会拉大状态机复杂度。

## 风险 / 权衡

- 样本详情页继续增长，可能变得拥挤 → 通过区块式主内容布局与页内展开表单控制信息密度。
- 固定 `category` 可能不足以覆盖全部异常 → 先用 3 类验证流程，后续再细化。
- 只支持 `sample` 级异常，可能无法表达“某条结果异常” → 当前以样本层面收口，后续再扩展到 `sample_result`。
- 异常不联动样本状态，可能被认为“不够智能” → 这是有意的 MVP 收敛，先保证异常自身闭环。

## Migration Plan

1. 在样本详情页设计异常处理区块，并放置在结果区块之后。
2. 接入当前样本的异常列表查询、异常创建与异常解决动作。
3. 为异常表单收敛固定 `category` 和 `severity` 选项，并确定 `reported_by` / `resolved_by` 默认值策略。
4. 验证样本详情页内结果、异常与关联工作流区块的共存与响应式布局。

回滚策略：
- 若异常区块的交互或布局出现问题，可先回退到只保留结果处理和关联工作流的样本详情页，同时保留异常 API 不变。

## 开放问题

- 异常录入表单更适合页内展开、Drawer 还是 Modal，需结合当前样本详情页密度决定。
- `reported_by` / `resolved_by` 默认值是否统一取样本 `collector.id`，还是允许用户显式修改，需要在实现前定口径。
- 是否需要在异常创建或解决成功后立即影响首页摘要刷新，还是仅在用户回到首页时自然更新。
