## 3.0 Laravel 迁移计划

本文档描述项目后端从当前轻量 PHP 实现迁移到 Laravel 的目标、边界与实施思路。

当前状态补充：Laravel 已经接管 `backend/` 中的主运行流量，迁移前轻量 PHP 骨架被保留在 `backend/legacy-lightweight/` 作为对照基线。

重要说明：

- 本文档描述的是迁移目标与计划，不是当前已完成实现。
- Laravel 迁移应建立在当前 P0 业务约束稳定的前提下推进。
- 迁移的重点是“替换后端承载层”，不是顺手重构全部业务模型。

### 3.0.1 迁移背景

当前轻量 PHP 实现已经足以支撑 P0 阶段的接口联调，但随着项目继续发展，后端即将持续增长以下复杂度：

- 认证与身份注入
- 权限控制
- 审计与操作留痕
- 更清晰的领域服务拆分
- Redis 队列与后台任务
- 更正式的数据库迁移与初始化体系

如果继续扩展当前手写骨架，项目将逐渐演化出一套自制小框架，长期维护成本和认知成本都会增加。

Laravel 被选中，是因为它更适合作为本项目长期的业务 API 与后台能力承载层。

### 3.0.2 迁移目标

**目标：**

- 将当前轻量 PHP API 承载层迁移到 Laravel。
- 保留现有 P0 API 契约，避免前端同步发生大规模重写。
- 保留现有数据模型和状态流转语义。
- 将数据库初始化方式逐步迁移到 Laravel migration / seeder。
- 为认证、权限、Redis 队列、审计能力建立更稳固的后端基础。

**非目标：**

- 不在迁移过程中重写 Nuxt 前端信息架构。
- 不在迁移过程中顺手大改业务对象关系。
- 不强制在第一阶段同时完成完整 Python 消费链路。
- 不把迁移与高级报表、对象存储、设备监控等后续能力绑定在一起。

### 3.0.3 迁移边界

#### 保持不变

- `/api` 路径设计
- 请求字段语义
- 响应结构语义
- 状态值与状态流转规则
- `inspection_tasks`、`samples`、`sample_results`、`exceptions`、`analysis_jobs` 等核心业务表语义
- Nuxt 前端的主要调用方式

#### 允许重建

- 路由分发方式
- 请求校验方式
- 响应封装方式
- 异常处理方式
- 数据访问层组织方式
- 数据库 migration / seeder 体系
- 业务服务拆分方式

#### 延后处理

- 完整认证授权体系
- 细粒度数据权限
- 完整 Redis -> Python 异步消费闭环
- 高级审计、通知、报表和文件处理能力

### 3.0.4 当前结构到 Laravel 的映射

```text
当前结构                           Laravel 目标结构
────────────────────────────────────────────────────────
backend/legacy-lightweight/public/index.php               -> backend/public/index.php
backend/legacy-lightweight/bootstrap.php                  -> backend/bootstrap/
backend/legacy-lightweight/app/Http/ApiKernel.php         -> backend/routes/api.php + Controllers
backend/legacy-lightweight/app/Http/Request.php           -> Laravel Request / FormRequest
backend/legacy-lightweight/app/Infrastructure/Database.php -> backend/config/database.php + DB 层
backend/legacy-lightweight/app/Service/P0ApiService.php   -> 按领域拆分为多个 Services
backend/legacy-lightweight/app/Support/JsonResponse.php   -> response()->json / API 响应层
backend/legacy-lightweight/app/Support/Validator.php      -> Laravel Validation
backend/legacy-lightweight/database/schema.sql            -> backend/database/migrations/
backend/legacy-lightweight/database/seed.sql              -> backend/database/seeders/
```

### 3.0.5 推荐的目标结构

迁移完成后的目标结构可大致理解为：

```text
backend/
├─ public/
├─ bootstrap/
├─ app/
│  ├─ Http/
│  │  ├─ Controllers/
│  │  ├─ Requests/
│  │  └─ Middleware/
│  ├─ Models/
│  ├─ Services/
│  ├─ Exceptions/
│  └─ Providers/
├─ routes/
│  └─ api.php
├─ config/
├─ database/
│  ├─ migrations/
│  └─ seeders/
└─ storage/
```

### 3.0.6 建议的分阶段实施顺序

即使最终选择一次性切换，逻辑上也建议按以下顺序组织工作：

1. 建立 Laravel 基础壳和运行环境。
2. 迁移数据库初始化体系到 migration / seeder。
3. 迁移 `dashboard` 域。
4. 迁移 `inspection_tasks` 域。
5. 迁移 `samples` 域。
6. 迁移 `sample_results`、`exceptions`、`analysis_jobs` 域。
7. 接入认证、权限和 Redis 队列能力。
8. 废弃旧轻量 PHP 骨架。

### 3.0.7 一次性迁移时的最低约束

如果实施时决定一次性迁移，而不是双轨渐进迁移，则建议至少遵守以下约束：

- API 契约先冻结，不与框架迁移同时改动。
- 数据表业务语义先冻结，不与框架迁移同时重构。
- 先用 Laravel 接住现有能力，再逐步吃到 Laravel 的认证、队列、权限红利。
- 不把“迁框架”和“改业务模型”混成同一轮工作。

### 3.0.8 数据层迁移策略

当前推荐的迁移策略不是重建业务模型，而是：

- 以现有 MariaDB 表结构为基础。
- 用 Laravel migration 表达当前结构。
- 用 Laravel seeder 表达当前初始化数据。
- 保留当前字段语义、状态值和约束口径。

换句话说：

```text
重写的是数据库迁移体系
不是业务表含义本身
```

### 3.0.9 服务层迁移策略

当前 `P0ApiService.php` 集中承载了多个域的业务逻辑。

Laravel 迁移后，推荐按领域拆分为多个服务，例如：

- `DashboardService`
- `InspectionTaskService`
- `SampleService`
- `SampleResultService`
- `ExceptionService`
- `AnalysisJobService`

这里应保留的是业务规则与状态机知识，而不是强行保留原文件边界。

### 3.0.10 风险与回滚原则

**主要风险：**

- Laravel 版 API 行为与当前前端契约不一致。
- 数据库 migration 表达与现有 SQL 语义不完全一致。
- Nginx、容器编排或环境变量切换导致入口异常。
- 迁移过程中顺手引入业务重构，造成范围失控。

**回滚原则：**

- 在 Laravel 版本完成契约对齐前，不应删除当前轻量实现作为参考基线。
- 若迁移阶段发现接口行为不一致，应优先回到契约对齐，而不是继续扩展新能力。
- 迁移目标未完成前，`docs/2.9-P0-迁移前实现基线` 仍应保留作为对照。

### 3.0.11 迁移完成判定

Laravel 迁移完成，不等于“Laravel 应用已经建起来”，而应满足以下条件：

- P0 API 全部由 Laravel 接管。
- Nuxt 前端无需因迁移而重写主流程接口调用。
- MariaDB 初始化改由 Laravel migration / seeder 主导。
- 旧轻量 PHP 路由与入口不再承载主流量。
- 容器、Nginx、前后端联调验证通过。

### 3.0.12 与现有文档的关系

后续讨论 Laravel 迁移时，建议按以下方式理解文档：

- `docs/2.4`：API 范围边界
- `docs/2.5`：数据模型与 MariaDB 目标实现口径
- `docs/2.6`：接口字段契约
- `docs/2.7`：状态流转约束
- `docs/2.9`：迁移前实现基线
- `docs/3.0`：Laravel 迁移目标与计划

这样可以避免旧实现文档继续污染后续迁移决策。

### 3.0.13 迁移后仍保留的过渡策略

当前迁移完成后，系统仍保留以下过渡性选择：

- 身份字段继续允许显式传参，后续再切换到 Laravel 认证态注入
- 服务层优先以 Query Builder 承载现有 SQL 语义，后续再逐步引入更深的 Eloquent 建模
- Redis 仍主要作为异步任务边界保留，后续再补齐 Laravel 队列与 Python 消费协作

这些选择是为了降低一次性迁移风险，不应被误解为长期能力上限。

### 3.0.14 迁移后的后续增强方向

Laravel 迁移完成后，优先级较高的后续增强方向包括：

- 将显式传参身份字段切换为认证态注入
- 建立角色与权限控制路径
- 引入更清晰的审计日志与操作留痕
- 将 `analysis_jobs` 与 Redis / Python 后台消费者真正接通
- 逐步评估 `Role`、`InspectionTask`、`Sample`、`AnalysisJob` 等模型是否需要更深的 Eloquent 化
