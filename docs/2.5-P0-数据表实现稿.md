## 2.5 P0 数据表实现稿

本稿基于以下文档整理：

- `docs/2.4-MVP-API-范围冻结稿.md`
- `docs/2.6-P0-API-字段草案.md`
- `docs/2.7-P0-状态流转草案.md`

目标是将当前阶段的概念级数据表设计，进一步收敛为可直接指导 MariaDB 建表与迁移设计的实现稿。

说明：本文档描述的是 P0 数据模型与 MariaDB 目标实现口径，而不是绑定当前轻量 PHP 骨架的专属实现方式。无论后端承载层是当前轻量实现还是后续 Laravel，本文档中的表语义、字段语义与状态口径都应尽量保持稳定。

本文档关注：

- 精确字段类型
- `NULL / NOT NULL / DEFAULT` 约定
- 索引与唯一约束
- 外键是否真正落库
- 建表顺序
- 初始化数据建议

当前阶段仍然遵循 `P0` 范围约束，不扩展到附件、任务事件、批次、设备监控等后续能力。

Laravel 迁移时，优先重建的是迁移工具链与后端组织方式，而不是顺手重构这里定义的数据模型。

```text
P0 实体主链路

users ----< inspection_tasks ----< samples ----< sample_results
  |                |                    |            \
  |                |                    |             \-> exceptions
  |                |                    |
  |                |                    \-> analysis_jobs
  |
  \----< user_roles >---- roles

exceptions 通过 resource_type + resource_id 关联 inspection_tasks / samples / sample_results
```

### 2.5.1 数据库实现约定

**数据库类型**

- 当前阶段以 `MariaDB` 为目标数据库。

**字符集与排序规则**

- 建议数据库和表统一使用：
  - `CHARSET = utf8mb4`
  - `COLLATE = utf8mb4_unicode_ci`

**主键策略**

- 所有主表主键使用 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 业务编码字段如 `task_code`、`sample_code` 只做唯一业务标识，不作为主键。

**时间字段策略**

- 统一使用 `DATETIME`。
- `created_at` 使用 `DEFAULT CURRENT_TIMESTAMP`。
- `updated_at` 使用 `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`。

**状态字段策略**

- 当前阶段统一使用 `VARCHAR(20)`。
- 状态值通过应用层和文档约束保证，不单独建字典表。

**JSON 字段策略**

- 当前阶段 `sample_results.raw_value`、`sample_results.normalized_value`、`analysis_jobs.params_json` 使用 `JSON` 类型。
- 在 MariaDB 中应同时通过应用层保证结构合法，不依赖数据库做复杂 JSON 查询设计。

**删除策略**

- 当前阶段不统一引入 `deleted_at`。
- 无效、取消、归档通过业务状态表达。

**外键策略**

- 单资源明确关联的字段采用真实外键。
- 多态关联字段 `exceptions.resource_type + resource_id` 不落数据库级外键，由应用层校验。

### 2.5.2 建表范围

当前阶段 `P0` 实现范围内建议落库的表如下：

- `users`
- `roles`
- `user_roles`
- `inspection_tasks`
- `samples`
- `sample_results`
- `exceptions`
- `analysis_jobs`

说明：

- `dashboard/summary` 不建表，使用聚合查询实现。
- `attachments`、`task_events`、`result_reviews`、`sample_batches` 暂不进入 `P0` 落库范围。

### 2.5.3 建表顺序建议

建议按以下顺序建表：

1. `users`
2. `roles`
3. `user_roles`
4. `inspection_tasks`
5. `samples`
6. `sample_results`
7. `exceptions`
8. `analysis_jobs`

这样可以避免大部分外键依赖问题。

### 2.5.4 users

**用途**

- 存储系统用户信息。

**建议建表口径**

| 字段名 | SQL 类型 | NULL | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 主键 |
| `username` | VARCHAR(64) | 否 | 无 | 唯一登录名 |
| `display_name` | VARCHAR(100) | 否 | 无 | 展示名 |
| `email` | VARCHAR(120) | 是 | NULL | 邮箱 |
| `status` | VARCHAR(20) | 否 | `'active'` | 用户状态 |
| `created_at` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |

**约束与索引**

- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_users_username (username)`
- `KEY idx_users_status (status)`

### 2.5.12 仪表盘聚合实现建议

`dashboard/summary` 不单独建表，建议通过聚合查询获得：

- `pending_samples`
  - 来源：`samples.status in ('registered', 'received', 'testing')`
- `today_inspection_tasks`
  - 来源：`inspection_tasks.planned_at` 位于当日范围内
- `open_exceptions`
  - 来源：`exceptions.status = 'open'`
- `queued_analysis_jobs`
  - 来源：`analysis_jobs.status in ('queued', 'running')`

### 2.5.13 当前阶段初始化数据建议

建议在第一版迁移或初始化脚本中至少准备以下基础数据：

**roles**

- `inspector`
- `analyst`
- `admin`

**users**

- 可先准备 1 个管理员测试账号
- 可选准备 1 个巡检员、1 个分析员测试账号

说明：

- 当前阶段不强制在数据库层准备任务类型、样本类型等字典初始化。
- 这些类型值先由应用层和测试数据控制。

### 2.5.14 当前阶段不纳入实现范围的表

以下表保留为后续演进候选，但不进入当前 `P0` 数据库实现范围：

- `attachments`
- `task_events`
- `result_reviews`
- `audit_logs`
- `sample_batches`
- `equipment`
- `dictionaries`

这样可以确保当前阶段优先把主业务对象、状态流转和异步任务链路实现稳定。
