## 上下文

当前 MVP 已经完成巡检任务列表/详情与状态推进、样本列表/创建/详情以及样本结果只读展示，`samples/:id` 页面已经成为样本处理链的中心节点。但最初冻结的 P0/MVP 主链明确要求包含“实验结果录入”，而当前前端仍停留在“看得到结果，但不能录入结果”的状态，导致样本处理链缺少关键闭环。

现有现实约束包括：

- Laravel 已提供 `POST /api/samples/{id}/results` 与 `GET /api/samples/{id}/results`，且 `StoreSampleResultRequest` 已允许以结构化 JSON 提交 `raw_value` / `normalized_value`。
- `sample_results` 的 P0 主流程状态默认仍为 `draft`，当前阶段不强制开放完整复核流。
- 样本状态推进按 P0 设计优先采用内聚处理方式，不单独增加 `receive` 动作接口；状态推进可由结果录入等业务动作触发。
- 当前仍保留显式传参身份字段策略，因此 `entered_by` 可以继续由前端显式传入。
- 样本详情页已提供结果列表、空态和关联动作区块，最适合继续承接结果录入，而不需要新增独立结果管理模块。

因此，本次设计的核心不是扩展新的后端域，而是在样本详情页中用最小表单与最小状态推进规则，补上结果录入这一环。

## 目标 / 非目标

**目标：**
- 在样本详情页中提供最小可用的结果录入动作。
- 将第一版 `result_type` 收敛为少量固定选项，优先支持 `salinity_test` 与 `ph_test`。
- 通过模板化 JSON 输入降低 `raw_value` / `normalized_value` 的录入门槛。
- 结果录入成功后刷新结果列表，并将 `registered` / `received` 的样本推进到 `testing`。
- 保持桌面端与移动端可访问，不因新增表单破坏当前响应式工作台结构。

**非目标：**
- 不在本次实现完整的结果编辑、删除、复核、批准或驳回流程。
- 不将样本结果做成独立模块或单独页面体系。
- 不在本次同步实现异常独立工作区或分析任务完整前端闭环。
- 不在本次引入认证态身份注入或替换现有显式传参策略。

## 决策

### 决策 1：结果录入附着在样本详情页内完成
- 选择原因：样本详情页已经是样本处理中心，并且已有结果列表区块与空态。将结果录入动作附着在此处，可以最短路径补齐主链，而无需新建 `sample-results` 独立页面和导航层级。
- 方案内容：
  - 在 `samples/:id` 详情页中加入“新增结果”动作。
  - 使用 Drawer、Modal 或页内展开表单承载录入，而不是单独新建结果页面。
- 放弃方案：
  - 单独新增 `sample-results/:id` 或 `/sample-results/new` 页面：超出 MVP 所需范围。

### 决策 2：第一版 `result_type` 固定为极小集合
- 选择原因：P0 文档只要求“能录、能查”，不要求复杂检测类型体系。现有示例已经稳定使用 `salinity_test`，再补一个同样简单且语义直观的 `ph_test`，足以证明系统具备真实结果录入能力，同时避免结果类型爆炸带来复杂动态表单。
- 方案内容：
  - 前端第一版仅提供 `salinity_test` 与 `ph_test` 两个选项。
  - 后端仍保留字符串 `result_type` 的开放性，不将数据库或接口锁死为固定枚举。
- 放弃方案：
  - 允许自由输入所有 `result_type`：更灵活，但会导致命名散乱，不利于 MVP 演示。
  - 一次性纳入更多类型如微生物/污染物筛查：业务感更强，但会显著增加输入模板和解释复杂度。

### 决策 3：`raw_value` / `normalized_value` 继续使用 JSON，但通过模板降低门槛
- 选择原因：现有后端接口与数据库都以 JSON 存储结构化结果，这为不同检测项目保留了弹性。与其为每个检测类型快速堆出专属表单，不如先保留 JSON 结构，并通过预填模板和最小校验来降低录入成本。
- 方案内容：
  - 当用户选择 `result_type` 时，自动为 `raw_value` 与 `normalized_value` 填入默认 JSON 模板。
  - 前端仅做两层最小校验：合法 JSON、且根结构为对象。
  - `normalized_value` 保持可选，允许用户先只录入原始值与结论。
- 放弃方案：
  - 空白 textarea 直接让用户从零填写 JSON：门槛过高。
  - 为 `salinity_test` / `ph_test` 专门构建字段化动态表单：会过早进入结果类型表单系统设计。

### 决策 4：录入结果后以内聚方式推进样本状态到 `testing`
- 选择原因：MVP 需要让“录入结果”带来可见的业务流动。若样本已有结果却仍停在 `registered`，用户体验会割裂。P0 状态流转文档已建议创建结果后将样本推进到 `testing`，因此适合在本轮以最小规则落地。
- 方案内容：
  - 当成功创建结果记录且样本状态为 `registered` 或 `received` 时，将样本推进到 `testing`。
  - 若样本已处于 `testing` 或更后续状态，则保持原状态不变。
  - 结果记录本身仍以 `draft` 作为初始状态。
- 放弃方案：
  - 录入结果后不改样本状态：会削弱主链的“前进感”。
  - 直接将样本推进到 `reviewed`：与当前不做复核流的 P0 语义冲突。

## 风险 / 权衡

- JSON textarea 对非技术型用户仍有门槛 → 使用预填模板、恢复模板和最小示例文案缓解。
- 固定 `result_type` 过少，可能显得像演示脚本 → 先用 2 个类型验证流程，后续按真实业务再扩展。
- 样本状态自动推进可能与未来 `receive` 动作冲突 → 规则限定为 `registered` / `received` -> `testing`，保留后续扩展空间。
- 在样本详情页继续堆动作，页面可能变重 → 保持本轮只增加“新增结果”，异常与分析入口可先保留为后续扩展位。

## Migration Plan

1. 在样本详情页设计并接入“新增结果”入口。
2. 为 `salinity_test` 与 `ph_test` 提供模板化 JSON 录入表单与最小校验。
3. 调用现有 `POST /api/samples/{id}/results`，在成功后刷新结果列表。
4. 在后端或现有样本处理逻辑中补齐结果录入后的样本状态内聚推进。
5. 验证新录入结果、样本状态变化与首页摘要口径的一致性。

回滚策略：
- 若结果录入表单体验或状态推进逻辑出现问题，可先回退到样本详情页的只读结果模式，同时保留后端结果接口不变。

## 开放问题

- 结果录入动作更适合 Modal、Drawer 还是页内展开表单，需结合当前 Nuxt UI 工作台交互密度决定。
- `entered_by` 默认值是取样本 `collector.id`、当前演示用户，还是允许用户必须手填，需在实现前统一口径。
- 是否在结果录入成功后立即触发首页摘要重新获取，还是仅在用户返回首页时自然刷新。
