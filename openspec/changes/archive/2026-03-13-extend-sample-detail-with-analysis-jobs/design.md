## 上下文

当前 MVP 已经完成样本详情页内的结果录入与异常处理，使样本处理链推进到“结果 -> 异常”。根据最初冻结的主链，异常之后还应承接“分析状态”，而 Laravel 后端已经具备分析任务创建、列表查询和详情查询接口，但前端尚未围绕当前样本提供发起分析任务和查看分析任务状态的入口。

当前现实约束包括：

- `analysis_jobs` 相关接口已存在，且当前阶段明确以“提交 + 状态查询”为主，不要求复杂结果体系。
- 样本详情页已经承担结果与异常处理，是样本处理中心，继续在该页挂接分析任务比新增独立分析平台更符合 MVP 收敛原则。
- 当前 `analysis_jobs` 数据模型允许附带可选 `params`，但 P0 目标不要求复杂参数编辑器。
- 当前仍保留显式传参身份字段策略，因此 `queued_by` 可继续由前端显式传入。
- Redis/Python 真消费闭环属于后续增强项，不是这一轮前端分析任务工作流的前置条件。

因此，本次设计重点是将分析任务作为“样本详情页中的下一步动作”接入，而不是同时建设完整分析后台或异步处理系统。

## 目标 / 非目标

**目标：**
- 在样本详情页中新增分析任务区块，支持围绕当前样本查看分析任务列表、发起分析任务与查看任务状态。
- 将第一版 `job_type` 收敛为极小固定集合，优先支持 `quality_assessment` 与 `anomaly_scan`。
- 保持分析任务区块与当前结果、异常区块形成清晰的主内容流，并适配桌面端与移动端。
- 复用现有分析任务接口与 `queued` 初始状态语义，不强制引入新的后端架构变化。

**非目标：**
- 不在本次新增独立 `/analysis-jobs` 工作区或单独的任务详情页。
- 不在本次实现复杂参数编辑器、任务取消、任务重试或自动轮询刷新策略。
- 不在本次打通 Redis/Python 真消费闭环或展示复杂分析结果可视化。
- 不在本次引入认证态身份注入，仍沿用当前显式传参策略。

## 决策

### 决策 1：分析任务区块附着在样本详情页主内容区
- 选择原因：样本详情页已经按“基本信息 -> 结果 -> 异常”的主链展开，分析任务自然应接在异常之后，形成完整处理工作流。将其继续放在主内容区，比塞进右侧辅助栏更适合承载任务列表与发起表单。
- 方案内容：
  - 样本详情页结构扩展为“基本信息 -> 结果 -> 异常 -> 分析任务 -> 关联工作流”。
  - 分析任务区块包含标题、说明、发起分析入口、页内展开表单和任务列表。
- 放弃方案：
  - 独立分析任务页面：超出 MVP 范围。
  - 右侧栏承载分析任务：空间不足，不利于移动端和状态卡片展示。

### 决策 2：第一版 `job_type` 收敛为两个固定选项
- 选择原因：MVP 的重点是让分析状态“可发起、可观察”，而不是完整分析能力建模。`quality_assessment` 与 `anomaly_scan` 既贴近当前样本结果/异常语境，又不会引导用户期待复杂模型系统已经完成。
- 方案内容：
  - 第一版前端只提供 `quality_assessment` 与 `anomaly_scan` 两个选项。
  - 后端仍保留 `job_type` 字符串开放性，不锁死数据库或接口枚举。
- 放弃方案：
  - 自由输入任意 `job_type`：会导致语义分散，不利于 MVP 演示与列表展示。
  - 一次性纳入更多类型如 `trend_analysis`：会过早抬高对历史分析能力的预期。

### 决策 3：分析任务第一版只提供最小发起表单
- 选择原因：当前后端创建分析任务所需核心字段只有 `sample_id` 与 `job_type`。如果第一版就暴露复杂 `params`，会迅速把工作流拖向“分析参数系统”。
- 方案内容：
  - `sample_id` 固定来自当前样本上下文。
  - 表单显式输入控制在 `job_type` 与 `queued_by`；`params` 先留空或隐藏，不作为主交互必填项。
  - 发起动作采用页内展开表单，保持与异常区块一致的交互节奏。
- 放弃方案：
  - 为不同 `job_type` 构建专属参数表单：超出 MVP 需要。

### 决策 4：分析任务第一版只做状态查看，不做任务操作与自动轮询
- 选择原因：P0 文档对分析任务的要求是“提交 + 状态查询”。若继续加入取消、重试、轮询、详情跳转，会迅速膨胀成任务平台。当前阶段应优先证明任务可被创建、可显示当前状态。
- 方案内容：
  - 分析任务列表最少展示 `job_type`、`status`、`queued_by`、`queued_at`。
  - 若后端已返回 `result_summary` 或 `error_message`，按状态补充展示。
  - 页面以手动刷新或自然刷新为主，不强制实时轮询。
- 放弃方案：
  - 第一版就做复杂状态管理、任务操作和历史详情：范围过大。

## 风险 / 权衡

- 样本详情页继续增长，区块较多 → 通过清晰顺序与统一区块样式控制信息密度。
- 固定 `job_type` 过少，可能显得分析能力较弱 → 先用最小集合跑通工作流，后续再扩展。
- 不暴露参数会限制某些分析任务场景 → 当前优先保证“可发起”，复杂参数留到下一阶段。
- 不做自动轮询，状态反馈可能显得不够即时 → 当前以最小状态查看达成 MVP 目标，后续再评估轮询或推送。

## Migration Plan

1. 在样本详情页主内容区新增分析任务区块，并放置在异常区块之后。
2. 接入当前样本的分析任务列表查询与最小发起表单。
3. 为 `job_type` 提供固定选项，并确定 `queued_by` 默认值口径。
4. 验证分析任务列表、状态展示与首页摘要 `queued_analysis_jobs` 的一致性。

回滚策略：
- 若分析任务区块交互或布局出现问题，可先回退到“结果 + 异常”的样本详情页，同时保留分析任务 API 不变。

## 开放问题

- `queued_by` 默认值是统一取样本 `collector.id`，还是允许用户显式修改，需要在实现前统一口径。
- 第一版是否要允许可选 `params` JSON 输入，还是完全隐藏参数字段，需要在实现前确认。
- 是否需要在分析任务创建成功后立即影响首页摘要刷新，还是仅在用户返回首页时自然更新。
