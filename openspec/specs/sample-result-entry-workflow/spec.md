# sample-result-entry-workflow 规范

## 目的
定义样本详情页内的最小实验结果录入工作流，使样本处理链从“结果只读”推进到真实可录入、可刷新、可推动状态前进的 MVP 闭环。

## 需求
### 需求:样本详情必须支持最小可用的结果录入动作
系统必须在样本详情页内提供结果录入入口，允许用户围绕当前样本新增实验或检测结果，而不能继续停留在只读结果展示。

#### 场景:打开结果录入表单
- **当** 用户在样本详情页执行“新增结果”动作
- **那么** 系统必须展示最小可用的结果录入表单

### 需求:结果录入第一版必须限制为极小结果类型集合
系统必须将第一版结果录入的 `result_type` 收敛为少量固定选项，优先支持 `salinity_test` 与 `ph_test`，禁止在当前 MVP 阶段同时开放无限制自由类型输入作为主交互方式。

#### 场景:选择结果类型
- **当** 用户在结果录入表单中选择结果类型
- **那么** 系统必须至少提供 `salinity_test` 与 `ph_test` 两个选项

### 需求:结果录入必须支持模板化 JSON 输入
系统必须允许用户以结构化 JSON 录入 `raw_value` 与可选的 `normalized_value`，并通过模板降低录入门槛。

#### 场景:选择盐度检测模板
- **当** 用户选择 `salinity_test`
- **那么** 系统必须为 `raw_value` 与 `normalized_value` 预填对应 JSON 模板

#### 场景:选择 pH 检测模板
- **当** 用户选择 `ph_test`
- **那么** 系统必须为 `raw_value` 与 `normalized_value` 预填对应 JSON 模板

#### 场景:校验 JSON 输入
- **当** 用户提交结果录入表单且 JSON 输入格式不合法
- **那么** 系统必须阻止提交并展示可理解的格式错误提示

### 需求:结果录入成功后必须刷新样本处理视图
系统必须在结果创建成功后刷新样本详情中的结果列表，并向用户提供明确反馈。

#### 场景:成功创建样本结果
- **当** 用户提交合法的结果录入表单
- **那么** 系统必须调用现有 `POST /api/samples/{id}/results` 接口创建结果记录
- **那么** 系统必须刷新当前样本的结果列表并展示成功反馈

### 需求:结果录入必须以内聚方式推进样本状态
系统必须在结果录入成功后以内聚业务规则推进样本状态，使样本处理链从登记阶段进入检测阶段。

#### 场景:已登记样本录入结果
- **当** 样本当前状态为 `registered` 且用户成功创建第一条结果记录
- **那么** 系统必须将样本状态推进到 `testing`

#### 场景:已接收样本录入结果
- **当** 样本当前状态为 `received` 且用户成功创建结果记录
- **那么** 系统必须将样本状态推进到 `testing`

#### 场景:检测中样本继续录入结果
- **当** 样本当前状态已经是 `testing`
- **那么** 系统必须允许继续创建结果记录
- **那么** 系统不得因重复录入结果而将样本推进到更后续状态

### 需求:结果录入状态必须参与页面级推荐下一步
系统必须将结果录入情况整合进样本详情页的页面级推荐下一步表达，使用户能够直接判断当前是否应优先补录结果，而不是仅在结果区块空态中被动获知。

#### 场景:样本尚无结果记录
- **当** 当前样本尚无结果记录
- **那么** 系统必须在样本详情页的页面级推荐下一步中将结果录入表达为优先动作之一

#### 场景:样本已有结果记录
- **当** 当前样本已经存在结果记录
- **那么** 系统必须避免继续将结果录入表达为唯一的页面级优先动作
