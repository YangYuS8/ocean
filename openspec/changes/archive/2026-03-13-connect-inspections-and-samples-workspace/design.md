## 上下文

当前仓库已经完成 Laravel 后端迁移，P0 API 由 `backend/` 中的 Laravel 应用承载，Nuxt 4 工作台首页也已接入真实摘要接口。但除首页外，`frontend/app/pages/inspections.vue` 与 `frontend/app/pages/samples.vue` 仍是占位页面，尚未将已有的 `inspection-tasks`、`samples` 与 `sample-results` API 兑现为前端可操作工作流。

这使系统目前处于一种“后端能力具备、前端核心链未接通”的状态：

- 首页可展示真实摘要，但无法继续进入真实巡检任务或样本管理流程。
- Laravel 已提供巡检任务查询、详情、状态推进以及样本登记、详情、结果列表接口。
- `exceptions` 与 `analysis-jobs` 虽然已有 API，但在当前 MVP 中更适合作为样本工作流的后续挂载点，而不是第一批独立工作区。
- 文档已明确认证、权限和 Redis -> Python 完整异步闭环属于迁移后的增强项，而不是这一轮 MVP 的前置条件。

因此，本次设计的核心不是新增后端能力，而是把现有 P0 API 组织成可演示、可操作、可继续扩展的前端业务闭环。

## 目标 / 非目标

**目标：**
- 将 `inspections` 工作区升级为真实业务页，支持列表、详情与 `start` / `submit` 动作。
- 将 `samples` 工作区升级为真实业务页，支持列表、创建和详情查看。
- 在样本详情中展示样本结果列表，作为后续异常、分析任务和结果录入的挂载基础。
- 保持与现有 Nuxt 4 Node/Nitro、Nginx 反向代理和 Laravel `/api` 接口约定兼容。
- 保持桌面端与移动巡检场景可访问，不因页面升级破坏当前工作台响应式结构。

**非目标：**
- 不在本次引入认证、权限或身份字段自动注入。
- 不在本次独立实现 `exceptions`、`analysis-jobs`、`reports`、`equipment`、`settings` 的完整业务页。
- 不在本次打通 Redis -> Python 异步消费闭环。
- 不在本次重写现有 P0 API 契约或重构 Laravel 领域模型。

## 决策

### 决策 1：先兑现“巡检任务 + 样本管理”两条核心前端工作流
- 选择原因：这两条线最接近 MVP 的业务主链，且后端接口已齐备。优先把占位页替换为真实工作流，比继续扩展后端能力更能提升系统的可演示性与可操作性。
- 方案内容：
  - `inspections` 提供任务列表、任务详情和状态推进动作。
  - `samples` 提供样本列表、样本创建、样本详情与结果列表只读展示。
- 放弃方案：
  - 先做认证/权限：价值高，但不是当前 MVP 最短板。
  - 先做 `analysis-jobs` 异步闭环：更适合在前端主链可用后推进。

### 决策 2：重要对象使用独立页面，重要动作优先附着在页面内完成
- 选择原因：MVP 需要尽快形成可用工作台，而不是构建完整页面体系。将 `inspections` 和 `samples` 作为独立页面，可以建立稳定的导航与信息层级；把创建和状态推进等动作附着在页面内，则可压缩范围、减少路由复杂度。
- 方案内容：
  - `inspections` 使用列表页 + 详情页。
  - `samples` 使用列表页 + 详情页。
  - 样本创建优先用弹窗、Drawer 或页内表单，不强制新增独立路由。
  - `start` / `submit` 动作直接位于任务详情页。
- 放弃方案：
  - 为每个动作单独新增页面：更完整，但超出 MVP 需要。

### 决策 3：样本结果在本次先作为详情页子区块只读接入
- 选择原因：样本结果是样本工作流的重要下游，但若在第一轮就同时做结果新增、异常登记和分析任务发起，范围容易膨胀。先把结果列表挂入样本详情，可以验证信息结构和接口接线，同时为下一轮扩展保留自然入口。
- 方案内容：
  - 在 `samples/:id` 详情页展示 `GET /api/samples/{id}/results` 返回的结果列表。
  - 若无结果，展示明确空态。
- 放弃方案：
  - 第一轮同步实现新增结果：可行，但会增加表单与错误处理复杂度。

### 决策 4：前端页面升级不改动现有 P0 API 契约，只在必要时暴露小补丁缺口
- 选择原因：当前 Laravel 迁移已完成，P0 API 契约是稳定基线。本轮应优先验证接口能否支撑真实前端工作流，而不是重新设计接口。若前端接线过程中暴露出字段不足或响应不便的问题，再以小补丁方式补齐。
- 方案内容：
  - 先按现有 `inspection-tasks`、`samples`、`sample-results` 接口接入。
  - 将缺口限定为字段补充、错误反馈或细小响应改进。
- 放弃方案：
  - 在本次同步大改接口字段语义：会损害当前迁移后稳定性。

## 风险 / 权衡

- 列表或详情接口字段不足，导致前端难以直接展示 → 先按现有接口接线，再将缺口收敛为小范围后端补丁。
- 巡检任务与样本页面一旦追求“完整工作台体验”，范围容易膨胀 → 严格限制第一轮只做列表、详情、关键动作与基本状态反馈。
- 移动端巡检场景下信息卡片过于复杂 → 优先使用卡片/分区式布局，避免桌面表格直搬到窄屏。
- 样本结果只读接入可能让用户预期“为什么不能新增结果” → 在页面结构上保留后续入口位置，但不承诺本轮就实现完整结果录入。

## Migration Plan

1. 盘点现有 `inspection-tasks`、`samples`、`sample-results` 接口字段与页面展示需求的匹配程度。
2. 将 `inspections` 工作区替换为真实列表页，并接入详情与状态推进动作。
3. 将 `samples` 工作区替换为真实列表页，并接入样本创建与详情展示。
4. 在样本详情中嵌入结果列表只读区块，补足空态、加载态和错误态。
5. 验证首页到任务/样本工作区的跳转路径与摘要联动体验。

回滚策略：
- 若真实工作流接入过程中出现严重问题，可暂时回退到占位页结构，同时保留已验证的后端接口能力不变。

## 开放问题

- 样本创建是采用弹窗/Drawer，还是直接使用独立页面，需结合当前 Nuxt UI 布局组件适配性决定。
- 巡检任务详情页是否同时展示关联样本入口，取决于现有详情接口是否已提供足够关联信息。
- 首页摘要是否需要在任务推进或样本创建后立即刷新，还是只依赖用户返回首页时重新拉取。
