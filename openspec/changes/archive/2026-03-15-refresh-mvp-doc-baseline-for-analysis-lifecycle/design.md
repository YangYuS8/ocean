## 上下文

当前仓库已经完成分析任务生命周期闭环的实现与 OpenSpec 归档，主规范也已经同步到 `sample-analysis-job-lifecycle`、`p0-api-foundation` 和 `frontend-mvp-operations-workspace`。但项目级设计文档中的若干关键基线仍然停留在较早阶段：分析任务在 `docs/2.4` 中仍主要被描述为“提交 + 状态查询”，`docs/2.6` 的字段草案尚未完整覆盖生命周期动作，`docs/2.9` 对当前实现现状的描述也未跟进到 Laravel 迁移后的最新闭环。

这会导致后续继续推进样本详情工作台、Redis/Python 异步执行链或验证路径时，团队在 OpenSpec、代码实现和项目说明文档之间切换时看到不同的“当前现实”。因此本次设计的重点不是引入任何新能力，而是将已经落地的分析任务生命周期和样本详情页工作流现实回写到项目文档基线中。

## 目标 / 非目标

**目标：**
- 让 MVP 关键文档与当前主规范和已实现行为保持一致，尤其是分析任务生命周期、失败后重新发起语义和样本详情页中的后续引导定位。
- 明确哪些文档属于“产品/API/状态基线”，并把已归档能力回写到这些基线文档中。
- 保持更新范围收敛，只同步已存在的能力，不借机扩展新需求。

**非目标：**
- 不新增任何应用代码、API 或数据库结构。
- 不启动 Redis/Python 真异步执行链设计。
- 不重写所有历史文档，也不把迁移前参考文档升级为新的长期架构文档。
- 不在本次引入新的 OpenSpec 主规范之外的大规模文档体系重构。

## 决策

### 1. 采用“关键文档校准”而不是“全量文档重写”

本次只更新对后续工作最有影响的文档：API 范围、字段草案、状态流转和实现/验证说明。这些文档直接影响下一步工作台设计、接口联调和执行链规划，因此优先级最高。

备选方案：
- 全量重写 `docs/`：完整但范围过大，会拖慢下一阶段产品推进。

### 2. 文档内容以当前 OpenSpec 主规范和已落地代码为准

本次校准不重新发明分析任务语义，而是以已经归档同步后的主规范为真实来源。这样可以避免文档再次出现与规范或代码不一致的平行定义。

备选方案：
- 直接按代码观感改文档：短期可行，但容易遗漏能力边界和规范化表述。

### 3. 保留“过程资源”和“业务资源”分层叙述

分析任务在文档中继续被定义为后台分析过程，而不是最终业务结果本身。样本结果与异常仍然是独立资源。这一层分离必须在项目级文档中被明确，否则后续工作台设计容易误把分析结果自动等同于业务结论。

备选方案：
- 在文档中把分析任务描述成“自动产出业务结论”的资源：会与当前实现和主规范冲突。

## 风险 / 权衡

- [风险] 文档校准容易被低估成“纯文字整理”，从而遗漏真正影响后续开发判断的边界。 → 缓解：围绕 API、字段、状态和验证路径四个最关键主题逐项更新。
- [风险] 历史文档中存在迁移前快照和当前稳定边界并存的情况，更新时容易混淆“参考基线”和“当前事实”。 → 缓解：在文档中明确哪些内容是迁移前对照信息，哪些内容代表当前 MVP 稳定现实。
- [风险] 若本次只更新分析任务相关章节，其他未变更章节仍可能保留历史措辞。 → 缓解：接受局部校准策略，但在 proposal 和 tasks 中明确本次范围只覆盖 analysis lifecycle 相关基线，不宣称完成全部文档清理。
