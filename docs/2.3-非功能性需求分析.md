## 2.3 非功能性需求分析

本节描述当前阶段建议遵循的非功能性要求，并区分现实可落地目标与后续演进方向。

重要说明：当前项目基于 `Nuxt + PHP + MariaDB + Redis + Docker Compose` 渐进建设，应优先关注可用、可维护、可恢复，而不是在现阶段承诺高可用集群、复杂容灾和重型平台化能力。

### 2.3.1 易用性 (Usability)

**当前目标**

- 工作台界面应清晰区分总览、样本、巡检、设备、报表、设置等主要模块。
- 巡检与录入流程应尽量减少自由文本输入，优先使用选择、状态流转和结构化表单。
- 页面应适配桌面端、平板和手机浏览，保证关键任务在窄屏下仍可完成。

**后续增强方向**

- 增加操作指引、标准示例和表单智能提示。
- 针对户外强光、手套操作等巡检场景做更细的交互优化。

### 2.3.2 性能与容量 (Performance & Capacity)

**当前目标**

- 常规工作台页面在正常开发部署环境下应保持可接受的加载速度。
- 列表、详情、摘要类接口应以“足够快、稳定返回”为优先目标。
- Python 分析等耗时操作应通过异步任务处理，避免阻塞核心业务接口。

**当前建议**

- 避免在当前阶段对并发量、响应时延设定过于激进且无法验证的硬指标。
- 对图片、附件等大资源优先采用分阶段接入策略，先支持基础上传与查看，再优化压缩和预览。
- 当前样本主图优先采用“文件落本地持久存储、数据库存引用”的方式，避免将图片内容直接塞入业务库。

**后续增强方向**

- 建立更明确的性能基线与容量评估。
- 引入更细粒度的缓存、缩略图和报表优化策略。

### 2.3.3 可靠性与可恢复性 (Reliability & Recoverability)

**当前目标**

- 核心业务数据应避免因普通操作失败而丢失。
- 分析任务、同步任务等后台流程应具备失败记录与可重试能力。
- 出现异常时，维护人员应能通过日志或状态信息快速识别故障点。

**当前建议**

- 以基础备份、错误记录和任务重试作为当前阶段重点。
- 不在当前阶段默认承诺 99.9% 可用率、自动故障切换、多活架构等企业级高可用目标。
- Python 自动检测 worker 应至少保留任务失败信息、可重试语义和基础运行日志，便于定位模型或图片输入问题。

**后续增强方向**

- 更完善的备份策略、任务恢复流程和运行巡检能力。
- 更高等级的存储冗余、对象存储和容灾方案。

### 2.3.4 安全性 (Security)

**当前目标**

- 接口访问应基于角色权限进行控制，避免越权访问。
- 关键操作应保留审计记录，包括新增、修改、删除、状态回退和结果复核。
- 前后端输入应进行基础校验，减少常见注入与非法参数风险。

**当前建议**

- 当前阶段优先实现基础认证授权、日志审计、输入校验和安全上传策略。
- 不在当前阶段默认引入过重的安全承诺，如全量字段加密体系、不可篡改审计链等，除非有明确合规要求。

**后续增强方向**

- 更细粒度的数据权限。
- 更严格的敏感字段保护和密钥管理。
- 更完整的文件扫描、审计追踪和合规能力。

### 2.3.5 兼容性与终端适配 (Compatibility)

**当前目标**

- 前端应在主流现代浏览器中正常使用。
- 关键页面应在手机、平板、桌面端保持基本可访问和可操作。
- 系统设计应优先适应当前 Web 工作台模式，而非默认依赖原生 App 能力。

**后续增强方向**

- 如果后续巡检场景确实依赖原生相机、GPS、离线数据库等能力，再单独评估移动端壳或原生方案。

### 2.3.6 可维护性与演进性 (Maintainability)

**当前目标**

- 系统模块应围绕清晰职责边界组织：Nuxt 前端、PHP 业务接口、Python 分析模块、MariaDB 核心数据、Redis 异步分发。
- API 设计应优先服务于稳定业务对象与工作台场景，避免过早扩展到复杂平台能力。
- 运行方式应保持与当前 Docker Compose、Nginx、Nuxt Node/Nitro 模型一致。

**当前建议**

- 当前阶段优先保持单体式清晰分层，而不是提前引入微服务、K8s 或分布式平台化改造。
- 文档、接口说明和基础日志应尽量完整，帮助后续继续演进。
- 当前阶段允许 Python worker 采用容器内自管依赖和项目内置模型文件，以换取更稳定的复现路径。

**后续增强方向**

- 引入更正式的 API 文档管理。
- 完善自动化测试、构建与部署验证。
- 随着规模增长，再评估更复杂的监控、编排和扩展策略。

### 2.3.7 当前阶段非功能性优先级

在资源受限前提下，建议非功能性目标按以下顺序排序：

1. 可用：核心流程能跑通。
2. 可追踪：状态、结果、异常有记录。
3. 可恢复：失败任务可重试，关键数据可备份。
4. 可维护：模块边界清楚，部署方式稳定。
5. 可扩展：为后续图片处理、分析任务、告警能力预留接口。

这意味着当前阶段应优先建设“稳健的基础工作台”，而不是一次性追求完整行业平台能力。
