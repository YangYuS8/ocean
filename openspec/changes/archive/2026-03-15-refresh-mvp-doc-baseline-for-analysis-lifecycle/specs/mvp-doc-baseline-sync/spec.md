## 新增需求

### 需求:MVP 关键设计文档必须与当前主规范保持一致
系统必须将项目级 MVP 关键设计文档中的稳定描述与当前 OpenSpec 主规范和已归档能力保持一致，避免在 API、状态流转和工作流定位上出现多套冲突基线。

#### 场景:文档回写已归档能力
- **当** 某项 MVP 能力已经实现、归档并同步到主规范
- **那么** 系统必须允许在关键项目文档中将该能力回写为当前稳定现实

#### 场景:避免文档继续保留过期能力边界
- **当** 项目级文档仍以旧边界描述当前能力
- **那么** 系统必须更新这些文档，使其不再与当前主规范或已实现行为冲突

### 需求:分析任务生命周期必须成为项目级文档基线的一部分
系统必须在项目级文档中明确分析任务已经从“提交 + 查询”扩展为“创建、最小状态推进、失败后重新发起和状态后续引导”的 MVP 闭环能力。

#### 场景:描述分析任务的当前 API 边界
- **当** 项目文档描述分析任务相关 API
- **那么** 系统必须反映当前已实现的最小状态推进动作和失败后重新发起语义

#### 场景:描述分析任务的当前产品定位
- **当** 项目文档描述样本详情页中的分析任务区块
- **那么** 系统必须将其表达为样本处理工作台中的过程型工作流区块，而不是仅有状态查询的附属列表

## 修改需求

### 需求:P0 分析任务接口必须支持异步任务记录与查询
系统必须提供分析任务创建、查询和最小状态推进接口，以支撑后续 Redis/Python 异步处理链路的渐进接入；在当前 MVP 阶段，前端最小工作流必须支持围绕样本详情页发起分析任务、查看状态、在成功或失败后获得后续处理提示，并对失败任务执行重新发起。

#### 场景:创建分析任务
- **当** 前端请求 `POST /api/analysis-jobs`
- **那么** 系统必须创建分析任务记录，并将初始状态设置为 `queued`
- **那么** 系统必须要求提供 `sample_id` 和 `job_type`
- **那么** 当前 MVP 前端工作流必须允许在样本详情页内完成该动作

#### 场景:查询分析任务列表
- **当** 前端请求 `GET /api/analysis-jobs`
- **那么** 系统必须返回分析任务列表，并支持按样本、任务类型、状态、发起人和入队时间范围筛选
- **那么** 当前 MVP 前端工作流必须允许围绕当前样本过滤并展示相关任务状态

#### 场景:查询分析任务详情
- **当** 前端请求 `GET /api/analysis-jobs/{id}`
- **那么** 系统必须返回任务状态、参数、结果摘要和错误信息

#### 场景:重新发起失败任务
- **当** 前端请求分析任务重新发起动作
- **那么** 系统必须仅允许基于状态为 `failed` 的任务执行该动作
- **那么** 系统必须保留原任务记录不变
- **那么** 系统必须创建新的分析任务记录，并将初始状态设置为 `queued`
- **那么** 当前 MVP 前端工作流必须允许在样本详情页内完成该动作
